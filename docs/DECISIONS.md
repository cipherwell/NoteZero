| 12 | Recovery-reset semantics | `resetWithRecoveryPhrase()` re-wraps the SAME phrase under a fresh salt; explicit phrase rotation is `rotateRecoveryPhrase(currentPassword)` | Frozen interface returns no new phrase from reset; silently rotating would strand users who wrote the old phrase. | 13 | External-activity lock deferral (SAF backup picker) | `beginExternalActivity()` / `endExternalActivity()` on `NoteRepository` bracket the system picker. While one is active, the background caused by the picker does NOT lock the vault; `onAppBackgrounded` records the pending background state instead and `endExternalActivity` locks immediately if the app is still backgrounded. The idle auto-lock timer is never cancelled, so a picker left open past `autoLockMinutes` still locks — there is no permanent suppression. A foreground return also clears the deferral state, so a lost picker result cannot weaken later background locks. | The SAF picker is a separate Activity: without the bracket every export/import would stop the app, lock the vault and lose the user's chosen `content://` URI. The secure default (immediate background lock) is preserved for every non-picker exit; only a bounded, recorded exception exists, and idle timeout remains the backstop. |
| 14 | Attachment storage, AAD, quota & backup | **App-private `NZAT` blobs** in `filesDir/attachments/<attachmentId>.nzb`: magic `NZAT` + version `0x01` + AES-256-GCM (`iv||ct||tag`) under the vault VMK with AAD `CryptoAad.attachment(noteId, attachmentId)` = `"notezero.attachment.v1|<noteId>|<attachmentId>"`. Refs (random id, display name, MIME, plaintext size, createdAt, lowercase-hex SHA-256) are content and live **inside** the v2 item envelope; `ItemCodec` still decodes v1 rows (empty list). Limits: 10 MiB/file (enforced while streaming, source size not trusted), 100/note, 512 MiB vault quota; count and byte quota both surface as `QUOTA_EXCEEDED`. Reads verify AEAD + exact size + SHA-256 and fail closed counted; imports are atomic (ciphertext temp+rename, ref added only after the blob; rollback deletes the blob); trash keeps blobs, delete-forever/empty-trash removes them, an unlock-time sweep deletes unreferenced blobs/temp files but is skipped entirely when any row failed to decode. Blob ids are validated (`[A-Za-z0-9_-]{1,64}`) before any file path is built (path-traversal guard). Backup format v2 carries refs + blobs, each blob still individually sealed under the source VMK/AAD; restore verifies SHA-256 against the ref, re-encrypts under the local VMK, dedupes by attachment id, skips+counts missing/invalid blobs without failing the note, and still imports v1 files. The v2 backup keeps the existing 64 MiB file cap as its OOM guard (attachment bytes count toward it; over-cap export fails cleanly, no partial file). | No new dependency, no plaintext/thumbnail/name on disk or in logs, no new permission; swapping blobs between notes/ids/vaults fails authentication; a single-process vault cannot rely on SQLCipher-style whole-file encryption, so each blob gets its own AEAD envelope like the item rows. Requiring SHA-256-on-read catches restore/disk corruption that a valid AEAD of rolled-back bytes would not. Repository-owned refs make editor autosave races safe. |
| 15 | Locked notes & folders ("lock note / lock folder", SPEC security feature) | **A per-record visibility gate, not a second encryption layer.** `Item.locked` / `Folder.locked` are content: they live **inside** the existing AES-256-GCM envelopes (`ItemCodec` payload **v3** trailing lock byte, `FolderCodec` payload **v2** trailing lock byte), never in a plaintext Room column. Locking/unlocking only rewrites that envelope: the same VMK, the same AAD (`CryptoAad.item(id, kind)` / `…|<FOLDER>`) and the same key hierarchy are used, so there is no per-note key, no re-encryption of any other row and no rotation on lock. The repository owns the flag like attachment metadata — `saveItem` preserves the stored value, so a stale editor autosave can never unlock a locked note; only `setItemLocked`/`setFolderLocked` change it. `verifiedLockedIds` is the memory-only, session-scoped set of ids whose locked content the UI may reveal; it is **never persisted**, starts empty on every unlock/setup, and is cleared by `lock()`, `close()`, "re-arm" (`clearLockVerifications`), and every background lock (screen-off / Activity stop) — but deliberately **not** while `beginExternalActivity()` defers the background caused by the SAF picker (decision #13), because the user did not leave. `markLockVerified(id)` is ignored while the vault is locked, so a verification cannot be smuggled into the next session. Re-authentication is `verifyMasterPassword` against the stored password envelope **without changing the session**, constant-time compared with the live VMK, rate limited by an injected clock (1 s → 4 s growing delay for failures 1–4, 30 s cooldown after 5, memory-only, reset on session boundaries); the char array is wiped on every path and blank input is rejected without counting as an attempt. Locked content is NOT hidden by the repository (`items`/`folders` still expose the decrypted records so the UI can render a mask); the UI must mask rows and filter before search/counts, and `ItemQueries`-based search is fed a pre-filtered list. Backups carry the flag inside the item/folder payloads, so a restore preserves lock state but never verification. | The SPEC feature is "hide it until re-auth" (handoff / shoulder-surfing scenario), not "protect it from an attacker with the VMK": while the vault is unlocked the plaintext already exists in RAM and the DB is already decryptable, so a second encryption layer would add key management and re-encryption risk without changing that threat. Reusing the authenticated envelope means the flag is tamper-evident and invisible at rest (no `locked` column, so a forensic reader cannot even tell which notes are locked), and the memory-only session set means a process restart, background or manual lock always re-masks. Refusing to gate on the repository keeps the UI free to show a consistent mask (title/placeholder, lock icon) and keeps search/count filtering in one place instead of a second data source. |

| 19 | Device-QA policies (Pixel 9 Pro XL, Android 17, font scale 1.15) | **(a) System bar appearance** follows the app theme: `NoteZeroTheme` sets `isAppearanceLightStatusBars`/`NavigationBars` from the resolved light/dark mode, so icons contrast with the surface instead of staying white on the light `#FAFAFA` background (previously an invisible status bar in light mode). **(b) Drawing canvas layout** uses a fixed 3:4 page (normalized stroke coordinates are unchanged, the PNG stays 3:4) inside a scrollable column, so the tool rows can never be pushed below the navigation bar at larger font scales; the full-screen dialog sets `decorFitsSystemWindows = false` and applies `WindowInsets.safeDrawing` itself exactly once. **(c) Biometric copy is failure-specific**: prompt errors are mapped to `UNAVAILABLE` (no hardware / key invalidated), `NOT_ENROLLED` (no fingerprint/face enrolled), `TEMPORARILY_UNAVAILABLE` (sensor busy), `LOCKOUT`, `CANCELLED` (silent) and `FAILED` (timeout/unable-to-process/vendor), instead of the single "Biometrics are not available on this device." message the user saw when Face failed on the device. **(d) The unlock-screen biometric CTA is gated on the repository's enrolled flag** (`NoteRepository.isBiometricUnlockEnrolled()`, backed by the wrapped-VMK Keystore check, non-secret and readable while locked), not merely on `canAuthenticate()`; a fresh vault no longer shows a button that can only fail. **(e) Backing out of the editor trashes a note only when it has no title, no body AND no attachments** — attachments are content, so an attachment-only note is kept. **(f) The settings banner is cleared when Settings opens**, so a stale "Vault locked."/error toast cannot greet a later visit. | These are user-visible bugs found by driving the real release build on the test device with the owner's display settings; fixing them keeps the Phase-5 "no misleading security copy" and "no silent data movement" bar. The enrolled-flag check leaks nothing (it only reveals whether a wrapped VMK exists, which the device already knows) and prevents useless prompts; moving a note to trash must never happen behind the user's back when they did attach something. |
| 20 | Create menu, code formats and encrypted PDF documents (increment 8) | **(a) Creation UX:** the Notes "+" is an icon-only FAB that opens a **bottom-sheet overlay** with Note / Drawing / Code / PDF. The sheet is an in-window overlay (scrim + bottom card with `create_overlay`/`create_scrim`/`create_sheet` tags), not a `Dialog`: on the edge-to-edge test device a full-screen dialog window was laid out taller than the visible display, which pushed the PDF option under the gesture bar at font scale 1.15; the overlay inherits the real window bounds/insets and its content is also scrollable/capped (device QA finding). Code files created from the menu (and code rows tapped in Notes) open the dedicated code editor; PDF rows open the PDF viewer. Note = `createNote`; Drawing = create a note then open the editor with a one-shot `openDrawingOnStart` request (plumbed NoteEditorScreen → AttachmentStrip, consumed on first composition); Code = name + extension picker, then `createItem(CODE_FILE)` + `saveItem(title)`; PDF = `createItem(PDF_FILE)` + encrypted attachment import, trashed again on import failure. **(b) Code formats** are an extensions-first catalog (27 well-known formats, `code/CodeFormats`): the extension is the file name suffix and the lexer language is the nearest supported one (`PLAIN` for formats without a grammar, so the editor never mis-highlights); a name typed with a known extension is kept as-is (`resolveName`), the picker rewrites it only otherwise; chips are technical labels (`.py`), not localised copy. **(c) PDF documents** are `ItemKind.PDF_FILE` (payload kind ordinal 2, appended so v1/v2 payloads still decode): a blank one-page PDF generated by pure-Kotlin `BlankPdf` (A4, empty content stream, computed xref/trailer) stored as an encrypted `application/pdf` `NZAT` attachment on the item through the normal import pipeline; title = deterministic `document-<timestamp>.pdf`. Backup v2 carries the kind (in the encrypted payload) and the blob with no special case. **(d) PDF viewing** uses the platform `PdfRenderer`, which requires a seekable file descriptor: the decrypted bytes are written to an ephemeral app-private cache file, rasterised to bounded in-memory bitmaps (≤ 8 pages, ≤ 1600 px long edge), and the file is deleted in a `finally` block; bitmaps are recycled on dispose; corrupt files/OOM fail cleanly with non-secret copy; export is the explicit decrypted-copy SAF flow. | The create menu keeps one obvious entry point while making file types explicit, and reuses the existing encrypted item/attachment/backup machinery instead of a parallel storage model: a PDF is an item with an encrypted blob, so trash/delete-forever/orphan-sweep/backup/quota/lock rules apply unchanged. Extensions-first formats let any common language be *created* without shipping a lexer for every grammar (wrong highlighting would be worse than plain text). The renderer temp file is the one place a decrypted document briefly touches disk: it is app-private cache (excluded from backup), bounded, deleted immediately after rasterisation, and the alternative (no in-memory seekable API) would mean not supporting PDF viewing at all — recorded in THREAT-MODEL §3.9/§6. |

| 18 | Phase-4 completion policies (drawing, export, tables, quick capture) | **(a) Drawing** is rendered in memory (white page, long edge ≤ 2048 px) and imported as an encrypted `image/png` attachment through the same `importAttachment` pipeline; if the encoded PNG would exceed the 10 MiB cap the renderer halves the resolution (min 256 px) instead of surfacing a size error. **(b) Note export** is available only as an explicit user action through SAF `CreateDocument` behind an "UNENCRYPTED copy" warning; Markdown and HTML are supported and the HTML renderer escapes all text/attributes and drops `javascript:`/`data:`/`vbscript:` link targets (labels stay as text). **(c) Tables** are edited in Markdown source: an insert-table dialog (1–20 rows/cols) inserts a GFM table at the caret and the overflow exposes row/column add/remove for the table under the caret; the block preview renderer is unchanged. **(d) Quick capture** is a static launcher shortcut that sends `com.cipherwell.notezero.SHORTCUT_NEW_NOTE` to `MainActivity`; the request survives a locked vault and is honoured only after unlock, creating the note through the normal encrypted repository path. | These complete the Phase-4 "iOS-like extras" without adding permissions: no camera, no storage permission, no share providers, no new dependency. Drawing re-render instead of erroring keeps the 10 MiB invariant while making the failure mode invisible to the user; the export allowlist prevents the only plaintext-egress feature from becoming an injection vector; quick capture never bypasses the lock or the encryption path. |
