| 13 | External-activity lock deferral (SAF backup picker) | `beginExternalActivity()` / `endExternalActivity()` on `NoteRepository` bracket the system picker. While one is active, the background caused by the picker does NOT lock the vault; `onAppBackgrounded` records the pending background state instead and `endExternalActivity` locks immediately if the app is still backgrounded. The idle auto-lock timer is never cancelled, so a picker left open past `autoLockMinutes` still locks — there is no permanent suppression. The secure default (immediate background lock) is preserved for every non-picker exit; only a bounded, recorded exception exists, and idle timeout remains the backstop. |
| 14 | Attachment storage, AAD, quota & backup | **App-private `NZAT` blobs** in `filesDir/attachments/<attachmentId>.nzb`: magic `NZAT` + version `0x01` + AES-256-GCM (`iv||ct||tag`) under the vault VMK with AAD `CryptoAad.attachment(noteId, attachmentId)` = `"notezero.attachment.v1|<noteId>|<attachmentId>"`. Refs (random id, display name, MIME, plaintext size, createdAt, lowercase-hex SHA-256) are content and live **inside** the v2 item envelope; `ItemCodec` still decodes v1 rows (empty list). Limits: 10 MiB/file (enforced while streaming, source size not trusted), 100/note, 512 MiB vault quota; count and byte quota both surface as `QUOTA_EXCEEDED`. Reads verify AEAD + exact size + SHA-256 and fail closed counted; imports are atomic (ciphertext temp+rename, ref added only after the blob; rollback deletes the blob); trash keeps blobs, delete-forever/empty-trash removes them, an unlock-time sweep deletes unreferenced blobs/temp files but is skipped entirely when any row failed to decode. Blob ids are validated (`[A-Za-z0-9_-]{1,64}`) before any file path is built (path-traversal guard). Backup format v2 carries refs + blobs, each blob still individually sealed under the source VMK/AAD; restore verifies SHA-256 against the ref, re-encrypts under the local VMK, dedupes by attachment id, skips+counts missing/invalid blobs without failing the note, and still imports v1 files. The v2 backup keeps the existing 64 MiB file cap as its OOM guard (attachment bytes count toward it; over-cap export fails cleanly, no partial file). | No new dependency, no plaintext/thumbnail/name on disk or in logs, no new permission; swapping blobs between notes/ids/vaults fails authentication; a single-process vault cannot rely on SQLCipher-style whole-file encryption, so each blob gets its own AEAD envelope like the item rows. Requiring SHA-256-on-read catches restore/disk corruption that a valid AEAD of rolled-back bytes would not. Repository-owned refs make editor autosave races safe. |
| 15 | Locked notes & folders ("lock note / lock folder", SPEC security feature) | **A per-record visibility gate, not a second encryption layer.** `Item.locked` / `Folder.locked` are content: they live **inside** the existing AES-256-GCM envelopes (`ItemCodec` payload **v3** trailing lock byte, `FolderCodec` payload **v2** trailing lock byte), never in a plaintext Room column. Locking/unlocking only rewrites that envelope: the same VMK, the same AAD (`CryptoAad.item(id, kind)` / `…|<FOLDER>`) and the same key hierarchy are used, so there is no per-note key, no re-encryption of any other row and no rotation on lock. The repository owns the flag like attachment metadata — `saveItem` preserves the stored value, so a stale editor autosave can never unlock a locked note; only `setItemLocked`/`setFolderLocked` change it. `verifiedLockedIds` is the memory-only, session-scoped set of ids whose locked content the UI may reveal; it is **never persisted**, starts empty on every unlock/setup, and is cleared by `lock()`, `close()`, "re-arm" (`clearLockVerifications`), and every background lock (screen-off / Activity stop) — but deliberately **not** while `beginExternalActivity()` defers the background caused by the SAF picker (decision #13), because the user did not leave. `markLockVerified(id)` is ignored while the vault is locked, so a verification cannot be smuggled into the next session. Re-authentication is `verifyMasterPassword` against the stored password envelope **without changing the session**, constant-time compared with the live VMK, rate limited by an injected clock (1 s → 4 s growing delay for failures 1–4, 30 s cooldown after 5, memory-only, reset on session boundaries); the char array is wiped on every path and blank input is rejected without counting as an attempt. Locked content is NOT hidden by the repository (`items`/`folders` still expose the decrypted records so the UI can render a mask); the UI must mask rows and filter before search/counts, and `ItemQueries`-based search is fed a pre-filtered list. Backups carry the flag inside the item/folder payloads, so a restore preserves lock state but never verification. | The SPEC feature is "hide it until re-auth" (handoff / shoulder-surfing scenario), not "protect it from an attacker with the VMK": while the vault is unlocked the plaintext already exists in RAM and the DB is already decryptable, so a second encryption layer would add key management and re-encryption risk without changing that threat. Reusing the authenticated envelope means the flag is tamper-evident and invisible at rest (no `locked` column, so a forensic reader cannot even tell which notes are locked), and the memory-only session set means a process restart, background or manual lock always re-masks. Refusing to gate on the repository keeps the UI free to show a consistent mask (title/placeholder, lock icon) and keeps search/count filtering in one place instead of a second data source. |

The renderer temp file is the one place a decrypted document briefly touches disk: it is app-private cache (excluded from backup), bounded, deleted immediately after rasterisation, and the alternative (no in-memory seekable API) would mean not supporting PDF viewing at all — recorded in THREAT-MODEL §3.9/§6. |
